## 3. Keycloak Realm ConfigMap

This is the command to create a ConfigMap from the Keycloak realm export:

Run from the repository root

```powershell
kubectl create configmap keycloak-realm-config `
--from-file=sammobank-realm.json=.\docker-compose\keycloak\realm\sammobank-realm.json
```

Run it from a directory where the relative path resolves correctly, or adjust the path.

If the ConfigMap already exists, `kubectl create` will report an error. Check the namespace and existing resource before deciding how to update it.

The realm export is documented at:

```text
docker-compose/keycloak/realm/sammobank-realm.json
```

## 4. Config Server Secret

The `k8/` manifests use a Kubernetes Secret named `configserver-secret` to securely provide credentials required by two services.

### Why is this Secret required?

The Secret contains the following credentials:

| Environment Variable | Used By | Purpose |
|---|---|---|
| `GITHUB_USERNAME` | Config Server | GitHub username for accessing the external configuration repository |
| `GITHUB_TOKEN` | Config Server | Personal Access Token used to authenticate with the `MICROSERVICES-CONFIG` repository |
| `MAIL_USERNAME` | Message Service | Email account used to send email notifications |
| `MAIL_PASSWORD` | Message Service | Email authentication password or App Password |

Config Server requires GitHub credentials to retrieve application configuration from the external repository: [ MICROSERVICES-CONFIG ](https://github.com/SoyaChunkz/MICROSERVICES-CONFIG)

Message Service requires email credentials to authenticate with the configured email provider and send email notifications.

### Secret Template

Create the file `3.2_configserver-secret.yml` inside the `k8/` directory using the following template:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: configserver-secret
type: Opaque
stringData:
  GITHUB_USERNAME: "your-github-username"
  GITHUB_TOKEN: "your-github-personal-access-token"
  MAIL_USERNAME: "your-email@gmail.com"
  MAIL_PASSWORD: "your-email-app-password"
```

Replace the placeholder values with your actual credentials.

**Security:** Never commit actual passwords, GitHub tokens, or other sensitive credentials to Git. Keep the populated Secret file local and add it to `.gitignore`.

### Create the Kubernetes Secret

Apply the Secret to your Kubernetes cluster:

```powershell
kubectl apply -f .\k8\3.2_configserver-secret.yml
```

Verify that the Secret was created:

```powershell
kubectl get secret configserver-secret
```

### Usage in Kubernetes and Helm

The same Secret is required by both deployment approaches:

- **Kubernetes manifests (`k8/`)** – The Config Server and Message Service deployments reference `configserver-secret` to retrieve their required environment variables.
- **Helm (`helm/`)** – The Helm deployments must reference the same Secret through their deployment templates and values.

Create the Secret in the target namespace before deploying the applications. Kubernetes Secrets are namespace-scoped, so the Secret must exist in the same namespace as the workloads that consume it.

When using Helm, ensure the charts reference the existing Secret rather than creating a separate Secret with different credentials.

> **Note:** The Secret resource is a Kubernetes resource. If you run the services directly through Docker Compose instead of Kubernetes, provide the corresponding credentials through environment variables or a local `.env` file. A Kubernetes Secret is not automatically available to Docker Compose.

## 5. Inspect Kubernetes Resources

The following commands can help inspect the cluster:

```powershell
kubectl get pods
kubectl get services
kubectl get deployments
kubectl get events --sort-by=.metadata.creationTimestamp
```

Use `-n <namespace>` when resources are in a specific namespace.

## 6. Kubernetes Dashboard

Run the port-forward command in one terminal and generate the token
in another terminal.

```powershell
kubectl port-forward -n kubernetes-dashboard svc/kubernetes-dashboard-kong-proxy 8443:443
kubectl create token admin-user -n kubernetes-dashboard
```

These commands assume the Dashboard service and `admin-user` service account already exist with those names and namespace.

Verify the resources and use appropriately scoped access.

## 7. Notes

- Kubernetes does not build application images. Images must be available to the cluster.
- Verify image names, tags, ConfigMaps, Secrets, service ports, and storage configuration before applying manifests.
- These manifests are just a basic setup; the separate Helm setup is documented under `helm/`.
